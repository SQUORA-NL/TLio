# with

> Evaluates a path **once** and runs a nested script with `@` addressing the node it selected —
> `forEach` for exactly one node. For the script that reaches into the same related record for many
> fields.

> **Looping pack**: requires `options.CommandsProvider.RegisterLooping<TNode>()` (the MCP server
> registers it).

## Syntax

```json
{
  "command": "with",
  "path": "<path selecting ONE node>",
  "commands": [ <nested commands> ]
}
```

XML: `<with path="…"><commands> … </commands></with>`; YAML: a `- command: with` mapping with `path` and `commands`.

> See [Notation Reference](../notation-reference.md) for quoting rules and escape sequences.

## Options

| Option | Type | Required | Default | Description |
|--------|------|----------|---------|-------------|
| path | string | yes | — | Path to the node `@` will address. Evaluated once. |
| commands | array | yes (no-op if empty) | — | Nested script run once, with `@` / `@.field` addressing the node. |

`title` and `description` are accepted like on every command.

**Functions in the path**: ✅ `=indirect()`, and `@`/`@.field` when nested inside another `with` or a `forEach`.

## Behaviour

- **One match** — the nested commands run with `context.CurrentNode` set to it, and the previous current node is restored afterwards, even when a nested command fails.
- **No match** — a warning, the block is skipped, the script continues.
- **Several matches** — the **first** is used and a warning says so. Visiting each is [`forEach`](ForEach.md)'s job.
- A nested command that fails fails the `with` (and stops the script), like a failing command in `forEach`.
- Nesting works through the ordinary call stack: `with` in `with`, `with` in `forEach`, `forEach` in `with` — the innermost active block is what `@` reaches, and each restores the outer one when it ends.

Inside the block `@` works exactly as in `forEach`: `path: "@.field"`, `path: "@"`, `value: "@.field"` and
`=fetch(@.field)`, `=if(equals(fetch(@.gender),'M'),…)`. A bare `=fetch(@)` is unsupported for the reason
given in [ForEach.md](ForEach.md#at-addresses-the-current-element). Paths that are not `@`-relative (`$.out.x`) still address the whole document.

## Nesting: `@` is shadowed, climb with `<--`

There is one `@`. Inside a nested `forEach` or `with`, it means the **innermost** node, and the outer
one is not reachable as `@`. To reach the node an outer `with` selected from inside a `forEach` over
one of its arrays, step up from the element with the parent token:

```json
{ "command": "with", "path": "$.team", "commands": [
    { "command": "forEach", "path": "@.members", "commands": [
        { "command": "add", "path": "@.owner", "value": "=fetch(@.<--.name)" } ] } ] }
```

In JSON/YAML the parent step is semantic: an array element's parent is the object that owns the
array, so one `<--` from a member is the team (`@.<--.<--` goes one object higher). Otherwise use an
absolute path, or copy the value into a scratch field before entering the inner block. This only
climbs *ancestors*; a node that is not an ancestor of the current one (the outer `forEach` element
when you are inside a `with` on a different branch) needs an absolute path.

## Formats

Works with all adapters; the path speaks the document's path language. XML notes:

- The current-item token is `.` — `<add path="./seen">`, `=fetch(./name)`.
- A **bare** `./name` as a `<value>` is literal text in XML, so write `=fetch(./name)` there. (JSON and YAML also resolve a bare `"@.name"` value.)
- XML paths do not carry positions: if the selected element has same-named siblings (an array item), `./field` resolves against the *first* sibling. Select a uniquely named element, or lift the item out first. This is the same limitation `forEach` has.

## Worked example: a 69-command mapping

A JSON → SOAP-XML mapping repeated this lookup 28 times — 13 fields for the policyholder, 13 for
the insured person, and one condition each:

```json
{ "command": "add", "path": "$.soap.body.policyHolder.firstName",
  "value": "=fetch($.masterAgreement[0].party[?(@.refKey == $.masterAgreement[0].policy[0].party[?(@.entityType=='policyHolder')].partyRef[0])].firstName)" }
```

Every one of the 26 `add`s (and the `ifElse` conditions) re-evaluates the whole nested filter. **After** — the
filter appears once per person and each field is a plain `@` read:

```json
{ "command": "with", "title": "fields of the policyHolder",
  "path": "$.masterAgreement[0].party[?(@.refKey == $.masterAgreement[0].policy[0].party[?(@.entityType=='policyHolder')].partyRef[0])]",
  "commands": [
    { "command": "add", "path": "$.soap.body.policyHolder.firstName", "value": "=fetch(@.firstName)" },
    { "command": "add", "path": "$.soap.body.policyHolder.city", "value": "=fetch(@.address[0].city)" },
    { "command": "ifElse", "condition": "=equals(fetch(@.gender),'M')",
      "ifScript":   [ { "command": "add", "path": "$.soap.body.policyHolder.title", "value": "Mr" } ],
      "elseScript": [ { "command": "add", "path": "$.soap.body.policyHolder.title", "value": "Mrs" } ] }
  ] }
```

The one-off lookups (beneficiary, payer) become
`=resolve($.masterAgreement[0].party[*], 'refKey', =fetch($.masterAgreement[0].policy[0].ref), 'lastName')`.

The full pair (invented data, no payload bodies) is `TLio.Parity.Tests/Equivalence/policy-mapping/`
(`script.original.json`, `script.rewritten.json`, `input.json`). `WithResolveEquivalenceTests` runs both through
`MultiFormatScriptRunner` (json → `convert` to XML, `arrayHandling: "repeated"`) and asserts **byte-identical XML**.

What it buys is readability first. Speed is real but modest: see [performance.md §3](../performance.md) —
about 20 % less time per run on this script.

## When to use

- Several commands read or write fields of the same related record.
- The record is found by a long or nested path that you would otherwise repeat.

## When NOT to use

- One field from a related record: `=resolve(...)` or a single `fetch` is shorter.
- Several nodes: [`forEach`](ForEach.md).
- The path depends on state a nested command changes — it is evaluated once, before the block.

## Common mistakes

- **Expecting every match to be visited.** Only the first is used (with a warning).
- **Moving or removing the selected node inside the block, then reading `@`.** `@` keeps pointing at the node that was selected.
- **A relative path in the block's own `path` of an outer-less `with`.** `@.x` at the top level has no current node; use an absolute path.

## Failure modes and what the trace tells you

| Situation | Trace outcome | What happened |
|---|---|---|
| `path` matched nothing | `noop` | Warning; block skipped; script continues. |
| `commands` empty | `noop` | Nothing to run. |
| More than one match | `success` | Warning; first match used. |
| A nested command failed | `failure` | The script stops, `CurrentNode` is restored. |
