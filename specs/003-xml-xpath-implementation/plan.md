# Implementation Plan: Native XPath Adapter + Adapter-Scoped Test Projects

**Branch**: `003-xml-xpath-implementation` | **Date**: 2026-03-28 | **Spec**: [spec.md](./spec.md)

## Summary

Two related deliverables:

1. **Native XPath fetcher** — a second `IItemsFetcher<XElement>` in `TLio.Xml` that accepts
   genuine XPath expressions (`address/city`, `//name`, `item[@id='1']`, `@attr`) without
   any stripping or rewriting. The existing `XPathItemsFetcher` (leading-slash, strip-based) is
   renamed `SlashPathItemsFetcher` so its actual behaviour is self-documenting. Both are usable
   via named factory methods on `XmlExecutionContext`.

2. **Adapter-scoped test projects** — `TLio.Xml.Tests` and `TLio.Yaml.Tests` replace the
   XML/YAML portions of `TLio.UnitTests`. Each project references only its own adapter assembly.
   Format-agnostic command/function/core tests remain in `TLio.UnitTests`.

| Gate | Article | Question | Answer |
|---|---|---|---|
| Format Neutrality | I | Do any Core/Commands/Functions changes risk importing a format-specific type? | **No.** All changes are inside `TLio.Xml` or new test projects. |
| Dependency Inversion | II | Is every new fetcher dependency injected via `IExecutionContext<TNode>`? | **Yes.** Factory methods produce a wired `ExecutionContext<XElement>`; no `new` in commands. |
| Generic-First | III | Does every new public API carry `<TNode>`? | **Yes.** `IItemsFetcher<XElement>` throughout. |
| Process/Execution separation | IV | Do all node reads/mutations go through `context.NodeAdapter` or `context.ItemsFetcher`? | **Yes.** No change to command layer. |
| Swappable Selection | V | Are paths always supplied by callers? | **Yes.** The whole point: callers choose which fetcher (slash-path vs. native XPath) via the `ExecutionContext` factory. |
| Test-First + Fixture files | VI | Will every full-script-execution test use file-based fixture files? | **Yes.** XML and YAML fixture files move with the tests; no inline `[TestCase]` for script execution. |
| Simplicity Gate | VII | Could this be done with fewer projects? | The new fetcher lives **inside the existing `TLio.Xml` project** (no extra production assembly). Two new test projects are the minimum needed to isolate XML and YAML adapter test dependencies. Verdict: **justified**. |
| No Leaking Internals | IX | Do `TLio.Core` public APIs expose only `TNode`-parameterised types? | **Yes.** No changes to `TLio.Core`. |
| Logging as Observability | X | Does every `Execute()` path call `LogInfo`/`LogWarning`? | **No change to command layer.** New fetcher has no `Execute()`. |

## Phase 0 — Research

### Decision: Native XPath path semantics

| Question | Decision | Rationale |
|---|---|---|
| What is `RootPathIndicator` for native XPath? | `.` (dot = current context / self) | Standard XPath "current node" is `.`. Root element is addressed simply by its name or via descendant axes. |
| How are absolute XPath paths handled (starting with `/`)? | Wrapped in `XDocument` so absolute XPath resolves correctly | `XPathSelectElements("/root/name")` fails on bare `XElement`; wrapping gives it a document context. |
| What does `GetPath(node)` produce? | `address/city` style (relative from root element, no leading `/`) | Matches what callers pass in; avoids ambiguity with slash-path notation. |
| `EnsurePath` with native XPath? | Only simple `a/b/c` paths supported for construction; predicate paths treated as read-only | Can't construct a node from `//name[@id='1']`. |
| `SplitParentAndLeaf` with native XPath? | Split at last `/` ignoring bracket-nested expressions | Same logic as JSON `SplitParentAndLeaf`. |
| Path format in NativeXPath fixture files? | `address/city` (no leading `/`) | Consistent with native XPath convention. |

### Decision: Test project layout

`TLio.Xml` and `TLio.Yaml` are format-specific. Tests for format-specific code should live in
format-specific test assemblies. This prevents `TLio.UnitTests` from accumulating references to
every adapter library, keeps CI times smaller per assembly, and makes the constitution's
format-neutrality checks trivially correct (grep `TLio.Core/TLio.Commands/TLio.Functions`
separately from `TLio.Xml.Tests`).

## Complexity Tracking

| Decision | Why | Simpler Alternative Rejected Because |
|---|---|---|
| Keep `SlashPathItemsFetcher` alongside `NativeXPathItemsFetcher` | Existing XML fixtures and `XmlScriptParser` use slash-path convention; removing it breaks backward compat | Renaming-only migration would require updating all existing XML fixture files and any user scripts |
| Two new test projects (`TLio.Xml.Tests`, `TLio.Yaml.Tests`) | Adapter-scoped testing removes format library leakage from the central test project | One monolithic project already works but violates the spirit of Article I for test code |
